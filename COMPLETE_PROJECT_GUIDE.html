🎯 Project Overview

Vision

Transform a headless C++ simulator into an interactive, visual learning tool for coverage path planning algorithms.

Why It Matters

  • Different algorithms have fundamentally different strengths
  • Speed vs. Coverage trade-off is critical for real deployments
  • Visual feedback helps researchers understand algorithm behavior
  • Quantitative metrics enable objective algorithm selection

Key Metrics Tracked

  • Coverage %: Percentage of floor cleaned (target: 90%+)
  • Steps: Total cell movements (lower is more efficient)
  • Revisits: Times already-cleaned cells visited again
  • Turns: Direction changes (affects real motor wear)
  • Overlap Ratio: Revisits ÷ Total steps (efficiency measure)

🏗️ Architecture & Design

Technology Stack

Component Technology Reason
Backend Simulator C++17 Performance, standard algorithms library
Frontend Visualizer HTML5 + Canvas Zero server, works offline
Data Format JSON + CSV Universal, easy to parse
Build System CMake Cross-platform, industry standard

Key Design Decisions

1. No ROS (Robot Operating System)

Decision: Use plain C++ + HTML instead of ROS

Rationale: ROS adds overhead without benefit for this simulation-only project. We avoid hardware dependencies, Linux-only constraints, and complex build pipelines.

2. Separate Binaries

Batch Mode: robot_vacuum_sim - Stable, unchanged, production baseline

Interactive Mode: robot_vacuum_interactive - New experimental features

Benefit: No cross-contamination risk, each optimized for its use case.

3. File:// Protocol (No Server)

Users double-click HTML file to run visualizer. No networking, no setup, works completely offline.

4. Realistic Obstacle Density

Only random obstacle placement (3-10% density). Removes unrealistic patterns (chessboards, corridors).

What Each Component Does

Simulation Engine (Simulation.cpp)

Responsibility: Core simulation loop for one algorithm run

Process:

  1. Initialize rover at start position
  2. Loop: Get direction from algorithm → Move → Mark cleaned → Record step
  3. Stop when coverage reached or max steps hit
  4. Return metrics

Grid Management (Grid.cpp)

Operations: isAccessible(), isCleaned(), markCleaned(), countCleanedCells()

Data: 2D array of cell states (EMPTY, OBSTACLE, CLEANED)

Room Generator (RoomGenerator.cpp)

Process:

  1. Place random rectangular obstacles
  2. Check connectivity via BFS
  3. Seal unreachable pockets
  4. Verify path to far corner
  5. Retry if validation fails

Trajectory Recorder (TrajectoryRecorder.cpp)

Captures: Algorithm name, room layout, step-by-step trajectory

Outputs: JSON file with complete run data for visualization

🤖 Algorithm Explanations

Algorithm 1: ZigZag (Deterministic)

→ → → ↓ ↓ ← ← ← → → → ↓ ↓ ← ← ←

Strategy: Sweep back-and-forth in rows

Pros Cons
✅ Fast (low steps)
✅ Minimal revisits
✅ Predictable		 ❌ Gets stuck in obstacles
❌ Incomplete on complex layouts
❌ Poor corners

Algorithm 2: Random Walk (Stochastic)

Strategy: Random exploration, biased toward unvisited cells

Priority: Unvisited → BFS search → Least-visited

Pros Cons
✅ Complete coverage
✅ No dead ends
✅ Adaptive		 ❌ Many revisits
❌ Very slow
❌ Inefficient

Algorithm 3: ZigZag + Wall-Follow

Strategy: Zigzag + wall-following escape when stuck

Pros Cons
✅ Escapes dead ends
✅ Faster than RandomWalk
✅ Good coverage		 ❌ Still incomplete
❌ Complex code

Algorithm 4: ZigZag + Random Escape ⭐ BEST

Strategy: Zigzag + random escape when stagnant

Pros Cons
✅ Balances speed & coverage
✅ Smart escape
✅ Adaptive		 ❌ Non-deterministic

📊 Performance Results

Moderate Rooms (6% Obstacles, ~94% Coverage Area)

Algorithm Steps Coverage % Revisits Turns Overlap Ratio
ZigZag 200,000+ 84.9% 199,698 29,034 0.998
ZigZag+WallFollow 850 90.2% 529 186 0.622
RandomWalk 200,000+ 32.8% 199,884 13,451 0.999
ZigZag+RandomEscape 1,275 90.2% 954 453 0.748

Key Findings

  1. ZigZag alone is insufficient - Gets stuck on moderate/complex layouts
  2. Hybrid methods are superior - Achieve 80-90% coverage with reasonable steps
  3. Random escape > Wall following - Better adaptive behavior
  4. RandomWalk is inefficient - Good fallback, not primary
  5. 3-10% obstacle density is optimal - Shows algorithm differences clearly

🐛 Bug Fixes & Improvements

Fix #1: ZigZag Stagnation Detection ✅

Problem: Algorithm got stuck in infinite loop at boundaries

Solution: Track steps without progress; escape stuck cells

Result: No more infinite loops

Fix #2: Room Path Connectivity ✅

Problem: Some rooms had sealed-off regions, skewing metrics

Solution: Validate path from start to far corner; reduce obstacle density

Result: All rooms have guaranteed complete path

Fix #3: RandomEscape Activation ✅

Problem: Escape mode never triggered in web simulator

Solution: Trigger on stagnation (not cleaning new cells), not just failure

Result: ZigZagRandom now produces different outputs

Fix #4: Obstacle Density Reduction ✅

Before: 8-20% density → 200,000+ steps to cover moderate rooms

After: 3-10% density → 358-1,275 steps on same rooms

Result: ~90-97% of room now cleanable

Fix #5: RandomWalk Initial Movement ✅

Problem: Algorithm got stuck at start position

Solution: Improved move selection logic; better BFS fallback

Result: Immediate exploration from start
